# 一、项目的根本目标

GitHub 对普通中文用户和编程初学者存在明显使用门槛：

* 页面、按钮、README、Issues、Pull Requests 等主要使用英文；
* 用户不熟悉 GitHub 的页面结构和术语；
* GitHub 搜索语法、仓库评估方法和操作流程较复杂；
* 用户进入陌生仓库后，不知道应该先看哪里；
* 遇到代码、报错、配置文件、Issue 或 PR 时，经常需要手动截图或复制内容，再转交给 AI；
* 用户难以判断项目是否适合自己、是否仍在维护、如何安装以及是否存在安全风险；
* 通用网页 AI 助手通常没有针对 GitHub 页面、搜索语法、新手导航和仓库评估进行深度适配。

本项目希望开发一个面向中文用户的 Chrome 扩展，使 AI 成为 GitHub 页面上的：

* 中文解释层；
* 新手导航层；
* 搜索转换层；
* 页面理解层；
* 受控操作辅助层。

用户不需要系统学习 GitHub 的全部术语和操作方式，也不需要频繁截图、复制和切换到其他 AI 工具。

---

# 二、产品定位

产品暂定为：

> 一个面向中文 GitHub 新手的浏览器 AI 助手。它能够理解当前 GitHub 页面、解释用户点击或框选的内容、把自然语言转换成 GitHub 搜索，并在受控范围内帮助用户完成页面导航和信息查询。

它不是：

* 通用浏览器自动化 Agent；
* 完整 IDE；
* 代码自动开发平台；
* ChatGPT 网页的附属插件；
* 依赖 ChatGPT Plus 订阅的产品；
* 第一版就能任意控制浏览器的全自动 Agent；
* 自动下载和执行陌生代码的工具。

# 三、预期核心能力

## 1. 当前页面解释

用户可以直接询问：

* 这个仓库是做什么的？
* 我应该先看哪些内容？
* 这个项目是否支持 Windows？
* 它适不适合新手？
* 应该下载哪个文件？
* 这个仓库是否仍在维护？
* 运行这个项目可能有什么风险？
* README 中哪些内容是我现在需要看的？
* 这个 Issue 是否已经解决？
* 这个 Pull Request 实际修改了什么？

扩展应自动读取当前 GitHub 页面中与问题有关的信息，并输出易懂的中文回答。

## 2. 点击元素后提问

用户进入“点击提问”模式后，可以点击：

* 按钮；
* 链接；
* 文件名；
* 代码；
* Issue；
* Release；
* 标签；
* 状态标识；
* 配置字段；
* 页面中的其他可识别元素。

扩展应读取：

* 元素类型；
* 元素文字；
* 目标链接；
* 必要属性；
* 附近上下文；
* 当前 GitHub 页面类型。

然后允许用户询问：

* 这是什么？
* 有什么作用？
* 我需要点击它吗？
* 这样操作有风险吗？
* 这段代码是什么意思？
* 这个文件是否重要？

## 3. 框选区域后提问

用户可以在页面上拖动框选一个区域。

扩展应优先提取：

* 框选区域内的文字；
* 链接；
* 代码；
* 按钮；
* HTML 结构；
* 附近必要上下文。

只有当结构化信息不足时，才截取局部图片并调用支持视觉输入的模型。

用户可以询问：

* 这一块是什么意思？
* 请翻译并解释这一部分；
* 哪些内容值得关注？
* 这里显示的问题是什么？
* 我下一步应该操作哪里？

## 4. 自然语言 GitHub 搜索

用户不需要学习 GitHub 搜索语法，可以直接输入：

* 帮我找适合 Windows 的开源文件整理工具；
* 最近一年仍在更新，至少有 100 个 Star；
* 在当前仓库中查找已经解决的代理问题；
* 只看与 Windows 安装有关的 Issues；
* 查找这个报错是否有人遇到；
* 找与当前仓库类似的项目。

AI 应把自然语言转化为：

* GitHub 搜索语句；
* GitHub API 查询参数；
* 或预定义的搜索工具调用。

执行前可以向用户展示简短的查询解释，但普通公开搜索不应要求用户反复确认。

## 5. 一键分析当前仓库

分析结果建议覆盖：

* 仓库用途；
* 主要语言和技术栈；
* 支持的平台；
* 安装方式；
* 是否存在可直接下载的 Release；
* 最新 Release；
* 最近更新时间；
* Star、Fork 等基础数据；
* 是否归档；
* 许可证；
* Issues 和 Pull Requests 状态；
* Actions 或持续集成状态；
* 新手使用难度；
* 可能涉及的权限和安全风险；
* 用户下一步最合理的操作。

回答应优先服务于普通中文用户，而不是只输出开发者术语和原始数据。

# 四、当前确定的基本技术方向

以下是已经形成的方向，不要求机械照搬，但偏离时必须有明确理由。

## 1. 独立 Chrome 扩展

项目优先采用：

* Chrome Manifest V3；
* TypeScript；
* Side Panel 作为主要交互界面；
* Content Script 读取页面并提供选择能力；
* Background Service Worker 处理扩展生命周期、消息和网络调用；
* 设置页面管理模型供应商、API Key 和用户偏好。

## 2. 直接接入 AI API

不依赖：

* ChatGPT 账号登录；
* ChatGPT Plus 订阅；
* ChatGPT Memory；
* ChatGPT App 作为产品的必要组成部分。

OpenAI 只是可选模型供应商之一，而不是产品的平台依赖。

架构应尽量允许未来接入：

* OpenAI；
* OpenRouter；
* Anthropic；
* Gemini；
* OpenAI API 兼容服务；
* 其他可能的文本和视觉模型。

## 3. 本地 Session 和记忆

扩展自行管理：

* 当前页面上下文；
* 对话 Session；
* 页面摘要；
* 最近对话；
* 用户明确设置的偏好；
* 必要的长期产品记忆。

不应把 AI 模型自身的上下文能力误认为可靠数据库。

## 4. 第一版优先个人使用

第一版可以采用用户自行提供 API Key 的 BYOK 方式。

但方案需要比较：

* 扩展直接调用 AI API；
* 本地 localhost 轻量代理；
* 远程后端代理。

应选择最适合个人原型和快速验证的路线，同时为将来发布预留迁移空间。

# 五、必须遵守的技术原则

## 1. DOM 优先

优先读取：

* 文本；
* 标题；
* 链接；
* 按钮；
* 表格；
* 代码块；
* ARIA 信息；
* 当前 URL；
* 页面类型；
* 仓库名；
* Issue 或 PR 编号；
* 页面中的结构化元数据。

可以直接读取网页结构时，不应完全依赖截图让视觉模型猜测。

## 2. GitHub API 第二

涉及以下数据时，优先评估 GitHub API：

* Repository；
* README；
* Releases；
* Issues；
* Pull Requests；
* Comments；
* Commits；
* Labels；
* Actions；
* 用户公开信息。

## 3. 视觉识别作为补充

视觉模型主要用于：

* 图片；
* 流程图；
* 截图；
* Canvas；
* 特殊渲染区域；
* 无法通过 DOM 正确读取的内容；
* 用户明确框选的视觉关系。

## 4. 模拟点击最后使用

第一版不应依靠模型根据截图猜测坐标并任意控制网页。

优先设计明确、可验证、白名单化的工具，例如：

* 打开指定 GitHub 页面；
* 打开 Releases；
* 打开 Issues；
* 搜索仓库；
* 搜索 Issues；
* 填写搜索条件；
* 高亮元素；
* 滚动到指定元素；
* 提取当前页面信息。

总体原则：

> DOM 优先，GitHub API 第二，视觉补充，模拟点击最后。

# 十、面向自主 Agent 的执行模型

最终方案需要适合下面这种使用方式：

> 我把项目目标、冻结基线和执行方案交给 ChatGPT App、Codex、Claude Code 或其他 Coding Agent。Agent 在授权范围内持续执行，只有到达必须由我确认的节点时才暂停。

## 1. 默认自主执行

在一个阶段内部，Agent 应自行完成：

* 读取相关项目文件；
* 实现代码；
* 补充类型；
* 更新测试；
* 运行测试；
* 修复普通错误；
* 更新技术文档；
* 检查差异；
* 整理阶段结果；
* 进入下一项已授权任务。

不应因为以下普通情况暂停：

* 需要创建文件；
* 需要重构内部代码；
* 测试首次失败；
* 出现普通 TypeScript 错误；
* 需要选择内部依赖；
* 需要更新配置；
* 需要增加测试覆盖；
* 需要调整目录结构；
* 需要修复自身引入的问题。

## 2. 仅在规定条件下暂停

执行 Agent 只应在以下情况暂停并请求我确认：

* 需要真实 API Key、Token 或账号授权；
* 将产生新的付费成本；
* 需要访问私有仓库；
* 需要扩大 Chrome 权限；
* 需要发送敏感数据；
* 需要执行不可逆的数据删除；
* 需要下载或运行高风险第三方程序；
* 需要发布到 Chrome Web Store；
* 需要创建公开仓库、公开 Release 或正式对外发布；
* 实际情况与冻结基线发生实质冲突；
* 存在多个影响产品方向的方案，无法依据既有原则作出选择；
* 当前阶段无法达到客观验收标准；
* 安全、合规或隐私风险无法在现有边界内解决。

## 3. 暂停时的输出格式

当必须暂停时，Agent 必须提供：

* 当前执行到了哪里；
* 已完成什么；
* 为什么必须暂停；
* 需要我决定的唯一问题；
* 推荐选择；
* 其他选项的实际影响；
* 我的回答会如何影响后续路径；
* 是否存在安全的默认处理方式。

不要一次提出大量与当前阻塞无关的问题。

## 4. 阶段完成不等于必须等待人工验收

如果阶段验收可以通过自动测试、静态检查、构建结果和明确证据完成，Agent 应记录结果并继续下一阶段。

只有方案明确标记为“人工体验验收”的节点，才需要我实际介入。

请尽可能减少此类节点。

# 十四、安全和隐私边界

## 1. 数据最小化

默认不应把整个页面完整发送给模型。

只发送：

* 用户问题；
* 必要页面元数据；
* 用户选中内容；
* 与问题相关的局部上下文；
* 必要页面摘要；
* 最近有限轮对话；
* 必要用户偏好。

## 2. 私有仓库

需要明确设计：

* 是否允许读取；
* 是否默认禁用；
* 是否每次提醒；
* 哪些数据可以发送给第三方模型；
* 如何防止误传。

## 3. 敏感信息处理

需要考虑检测和遮蔽：

* API Key；
* GitHub Token；
* Cookie；
* 密码；
* 私钥；
* `.env` 内容；
* 个人身份信息；
* 其他高风险凭据。

## 4. Prompt Injection

GitHub 页面、README、Issue、代码注释和用户生成内容均应视为不可信数据。

页面文字不得：

* 覆盖系统规则；
* 要求模型泄露密钥；
* 要求模型调用未授权工具；
* 要求忽略用户权限边界；
* 被解释为执行 Agent 的系统命令。
